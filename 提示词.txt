# 追星周边拼车平台 MVP 网页开发

请作为一名全栈开发工程师和 UI/UX 设计师，帮我直接开发一个完整、可运行、可交互的追星周边拼车平台网页。

不要只生成静态原型，需要实现完整的前端业务流程。

## 一、产品定位

这是一个帮助粉丝发起、寻找和加入偶像周边拼车的平台。

主要有两类用户：
- 车主：发起拼车、管理车次、确认拼成。
- 车员：浏览拼车、选择商品位置、加入拼车、进入拼车群。

同一个用户可以同时作为车主和车员。

## 二、技术要求

使用 React + TypeScript + Tailwind CSS。

使用 localStorage 保存数据，无须配置后端。

使用模拟账号切换身份，使用模拟支付，不接入真实支付接口。

所有页面使用简体中文，支持桌面和移动端。

## 三、核心页面

### 1. 首页 / 拼车广场

展示正在招募的拼车。

支持：
- 搜索拼车
- 按商品和成员位置筛选
- 查看剩余位置
- 点击查看拼车详情

### 2. 发起拼车

车主填写：
- 拼车标题
- 活动名称
- 商品名称
- 商品价格
- 开放的位置及数量
- 截单时间
- 拼车说明

提交后创建拼车，并展示在广场。

### 3. 拼车详情

展示：
- 车主昵称
- 活动与商品信息
- 价格
- 可选位置
- 已占位置
- 截单时间
- 拼车规则

车员选择空余位置后，点击加入拼车。

进入模拟支付确认页面，确认后完成上车。

已占位置不可重复选择。

### 4. 我的拼车

分为：
- 我加入的拼车
- 我发起的拼车

可以查看车次状态并进入详情。

### 5. 车主管理

车主可以：
- 查看车员名单
- 查看已占位置
- 查看拼车进度
- 点击“确认拼成”

确认后更新车次状态，并自动创建该车次的站内群聊。

### 6. 拼车群聊

每辆拼成的车自动对应一个群聊。

实现：
- 展示群成员
- 自动生成群昵称，允许修改
- 自动生成群公告模板，车主可以修改
- 群成员发送和查看文字消息

群聊使用本地模拟数据，不需要实时通信服务。

## 四、模拟数据

预置 NCT DREAM 周边拼车示例。

包含多个车主、不同商品、不同成员位置以及不同拼车状态。

示例数据只用于演示，不代表真实活动信息。

## 五、交互要求

所有主要按钮必须真实可用。

确保以下流程可以完成：

车主发布拼车 → 车员在广场找到车次 → 选择空余位置 → 模拟支付 → 加入拼车 → 车主确认拼成 → 自动建群 → 车员进入群聊。

需要提供基本的表单校验、操作反馈、空状态和错误提示。

页面刷新后，本地数据应保留。

## 六、UI 设计

设计风格：简洁、现代、轻量化，适合年轻粉丝使用。

采用浅色背景和柔和的紫色作为主要强调色。

重点做好：
- 顶部导航栏
- 拼车信息卡片
- 商品位置选择界面
- 拼车进度展示
- 发布拼车表单
- 群聊界面

布局清晰，交互直观，避免不必要的复杂功能。

## 七、开发要求

请直接生成完整可运行的网页项目，而不是只提供设计建议。

优先完成所有页面之间的导航与核心业务闭环。

确保模拟支付、位置占用、拼成确认和自动建群之间的数据状态正确关联。

完成后提供网页预览和运行说明。

不要自行扩展上述范围之外的功能。

# DREAM CAR V1.1 — 物流追踪与地址管理模块

你是一名资深全栈工程师、产品经理和 UI/UX 设计师。

请基于当前已经开发完成的 DREAM CAR 追星周边拼车平台，进行 V1.1 增量开发。

## 一、开发原则

1. 保留当前所有已经实现的页面、功能、交互和数据。
2. 不要重新创建项目，不要重构与本次需求无关的模块。
3. 首先检查现有项目的技术架构、数据结构和状态管理方式，再进行修改。
4. 沿用现有网页的视觉设计、组件风格、导航方式和交互习惯。
5. 只增加物流追踪、地址管理、到货检查和国内发货功能。

7. 所有新增功能必须可以实际操作，不能只有静态界面。
8. 暂不接入真实物流 API、短信服务和支付接口。
9. 所有物流节点、通知和发货信息使用模拟数据或车主手动录入。
10. 不要自行扩展本次需求之外的功能。

## 二、完整业务流程

现有业务流程：

车主发布拼车 → 车员选择位置 → 模拟支付 → 加入拼车 → 车主确认拼成 → 系统自动建群。

在此基础上新增：

车主完成官方下单 → 国际物流开始 → 全体车员查看国际物流 → 系统提醒车员补充收货地址 → 车主收到国际包裹并完成检查 → 车主打包、录入国内物流 → 车员查看个人物流信息。

国际物流追踪与地址收集应当并行进行。

## 三、模块一：国际物流追踪

### 1. 车主端

在已经拼成的车次管理页面中，新增「物流管理」入口。

车主可以：
- 填写国际物流公司。
- 填写国际物流单号。
- 填写物流查询链接（可选）。
- 手动更新国际物流状态。
- 填写物流状态说明。
- 记录物流状态更新时间。

国际物流状态包括：
1. 等待发货
2. 国际运输中
3. 清关 / 转运中
4. 国内运输中
5. 车主已签收
6. 到货检查完成

车主修改状态后，保存到当前车次的数据中。

### 2. 车员端

在「我的拼车」和车次详情中增加国际物流查看入口。

同一车次的所有车员都能查看：
- 国际物流公司
- 国际物流单号
- 物流查询链接
- 当前物流状态
- 物流更新时间
- 物流进度时间线

所有车员查看的是同一份国际物流信息。

国际物流信息只能由对应车主修改。

### 3. 地址收集触发

当车主首次将国际物流状态更新为「国际运输中」或后续运输状态时：

- 系统自动开启该车次的地址收集。
- 为所有已确认加入该车次的车员生成站内提醒。
- 在车员的「我的拼车」中展示「待补充收货地址」提示。
- 提供「填写收货地址」按钮。

同一车次不得因为车主重复修改物流状态而重复创建相同的地址收集任务。

## 四、模块二：个人地址管理

在个人中心新增「我的地址」页面。

### 1. 地址管理功能

用户可以：
- 新增地址。
- 查看已保存地址。
- 编辑地址。
- 删除地址。
- 设置默认地址。
- 添加地址标签，例如「学校」「家」「宿舍」。

每条地址包含：
- 地址 ID
- 所属用户 ID
- 地址标签
- 收件人姓名
- 联系电话
- 省份
- 城市
- 区县
- 详细地址
- 是否默认地址

### 2. 地址管理规则

- 同一用户可以保存多个地址。
- 同一用户最多只有一个默认地址。
- 设置新的默认地址时，自动取消原默认地址。
- 删除默认地址后，允许用户重新设置默认地址。
- 用户只能管理自己的地址。
- 不同模拟账号之间的地址不能混用。
- 删除地址需要二次确认。
- 所有地址数据在页面刷新后仍然保留。

## 五、模块三：车员补充收货地址

当车次开启地址收集后，车员可以进入地址填写页面。

提供两种方式。

### 方式 A：使用已保存地址

展示当前账号的地址簿。

用户可以：
- 查看所有已保存地址。
- 选择其中一个地址。
- 默认优先展示默认地址。
- 确认将该地址用于本次拼车。

### 方式 B：填写临时地址

用户可以手动填写：
- 收件人姓名
- 联系电话
- 省市区
- 详细地址

提供复选框：

「同时保存到我的地址簿」

如果勾选，提交时将该地址新增到个人地址簿。

如果未勾选，只保存到本次拼车订单中。

### 重要数据规则

个人地址簿与拼车订单收货地址必须独立存储。

提交地址时，应将完整地址信息复制为当前订单的地址快照。

后续修改或删除个人地址簿中的地址，不得自动改变已经提交的拼车订单地址。

车员修改当前订单地址，也不得自动修改个人地址簿。

### 2. 车员端

地址状态包括：

## 七、模块五：到货检查

当车主收到国际包裹后，可以：

1. 将物流状态更新为「车主已签收」。
2. 检查商品。
3. 点击「确认到货检查完成」。

点击确认后：
- 当前车次进入国内发货准备阶段。
- 普通地址收集阶段结束。
- 未提交地址的车员标记为「逾期未提交」。
- 车主仍可向未提交地址的车员发送催促提醒。
- 未提交地址的车员仍可通过逾期补交入口提交地址。

已经提交地址的车员，可以查看自己的地址信息。

如果车员在打包或发货前需要修改地址，应允许修改；已经发货的订单不允许直接修改收货地址。

- 当前发货状态。

车员只能查看自己的国内物流信息，不得查看其他车员的个人收货地址或快递单号。

- 0–59 分：禁止加入新拼车和发起新拼车。

信誉分低于阈值时，在相关页面展示限制原因及申诉入口。

权限校验必须实际生效：
- 发布拼车时检查用户信誉分。
- 加入拼车和模拟支付前检查用户信誉分。
- 不允许仅通过隐藏按钮实现权限限制。

被限制的用户仍然可以：

- 查看和处理现有群聊。
- 查看物流。

- 处理已有订单的必要履约事项。
- 查看信誉记录并提交申诉。

## 五、信誉加分规则

车主完成一辆车的全部履约流程：+2 分。

车员正常完成一次拼车：+1 分。

同一车次同一用户只能获得一次对应奖励。

正常履约奖励每个自然月最多累计 +5 分。

信誉分最高为 100。

加分必须根据实际订单完成状态触发，不得仅凭点击按钮反复加分。

## 六、信誉扣分规则

以下事件需要经过模拟平台管理员核实后才能扣分：

- 车主无故取消已成团车次：-10 分。
- 车主无合理说明延迟发货：-5 分。
- 车员擅自退出已成团车次：-5 分。
- 提供虚假物流信息：-15 分。
- 严重欺诈、恶意骚扰等违规行为：根据具体违规类型扣除 20–40 分。

投诉提交后不立即扣分。

同一违规事件只能扣分一次。

- 事件 ID

## 二、核心产品原则

### 2.1 拼车是核心业务实体

DREAM CAR 的核心业务是：

车主发布拼车 → 车员选择商品或成员位置 → 确认规则 → 模拟付款 → 成功占位 → 群内协商 → 成团 → 下单 → 物流履约。

所有功能应围绕拼车展开。

### 2.2 首次购买与后续加购是同一种操作

“承接空位”只是现实拼车过程中对补充购买的描述，不应被设计成独立的业务系统。

车主和车员都可以在符合规则的情况下，再次购买本车剩余商品或成员位置。

### 2.3 群聊是拼车的附属功能

群聊不具有独立于拼车的业务生命周期。

只有当一辆拼车出现首位成功占位的车员时，才自动创建对应群聊。

群聊列表仅用于集中查看已有拼车群的信息，不允许用户脱离拼车单独创建群聊。

### 2.4 减少重复入口

每个核心任务应有清晰的主要入口。

允许合理的快捷入口，例如从“我的拼车”和“群聊列表”进入同一个群聊，但不得让同一功能在多个页面重复出现，造成导航混乱。

# 三、需求一：取消独立承接系统，统一为加购

### A. 我参与的

# 六、需求四：新增群聊列表

## 6.1 产品定位

群聊是拼车的附属功能。

**群聊列表只是已有拼车群的集中查看入口，不是独立社交功能中心。**

群聊的创建依赖于拼车占位。

## 6.2 群聊创建规则

- 车主发布拼车时不创建群聊。
- 首位车员成功占位后自动创建该车群聊。
- 创建时自动加入车主和首位车员。
- 后续成功占位的车员自动加入已有群聊。
- 已有车员再次加购，不重复入群。
- 同一辆拼车最多只能有一个有效群聊。
- 群聊与成团状态解耦。
- 已成团、已下单的拼车继续保留原群聊。

请复用 V1.3-A 已实现的群聊创建逻辑，不要重新开发第二套建群机制。

## 6.3 群聊列表

新增一级导航“群聊”。

该页面只展示当前用户有权访问的、已经创建的拼车群。

每个列表项展示：

- 关联拼车名称
- 最新一条消息摘要
- 最新消息时间
- 当前拼车状态
- 未读消息数量（仅在存在可靠已读数据时展示）

建议按最新消息时间倒序排列。

没有任何已加入拼车群时，显示合理的空状态说明，可引导用户前往拼车广场寻找拼车，但不提供独立创建群聊功能。

## 6.4 群聊入口

保留两种访问路径：

路径 A：

群聊列表 → 选择已有拼车群 → 群聊页面

路径 B：

我的拼车 → 选择已参与或已发起的车次 → 进入该车群聊

两条路径必须进入同一个群聊实例。

## 6.5 禁止扩展的功能

本次不开发：

- 独立创建群聊
- 搜索陌生群聊
- 申请加入群聊
- 邀请陌生用户入群
- 脱离拼车的社交群组
- 独立群聊管理员体系
- 与拼车无关的私聊系统

群聊的成员资格应以现有拼车参与关系及权限规则为依据。
